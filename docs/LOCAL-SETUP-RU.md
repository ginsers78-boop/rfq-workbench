# Запуск RFQ Workbench на своём компьютере

**Статус: незавершённая портфолио-бета.** Полный список доработок находится в [ROADMAP](../ROADMAP.md). Если репозиторий соберёт достаточно звёзд и интереса сообщества, автор вернётся к разработке, выпустит обновления и завершит оставшиеся функции. Срок и порог звёзд пока не объявлены.

Это локальное приложение для одного пользователя. Готовы загрузка документов, локальное распознавание сканов/изображений, проверка позиций, справочник поставщиков и подготовка RFQ с Excel-шаблонами ответа. Gmail и расчёт итоговых котировок ещё не реализованы. Публиковать этот сервер в интернете нельзя: в нём нет многопользовательской авторизации.

## Первый запуск

1. Установите Python 3.11 или новее с официального сайта Python. При установке отметьте **Add python.exe to PATH**.
2. Установите Ollama с официального сайта Ollama. Запустите приложение Ollama.
3. Откройте PowerShell. Если модель ещё не установлена, выполните `ollama pull qwen3.5:9b`. Это бесплатная загрузка нескольких гигабайт; для комфортной работы нужна подходящая видеокарта и оперативная память. Модель не входит в репозиторий; повторная загрузка уже установленной модели не нужна.
4. Откройте папку проекта, щёлкните адресную строку Проводника, введите `powershell` и нажмите Enter. Терминал откроется в нужной папке.
5. Создайте отдельное окружение и установите бесплатные библиотеки:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

6. Запустите приложение:

```powershell
.\.venv\Scripts\python.exe -m rfq_workbench serve
```

7. Откройте в браузере **http://127.0.0.1:8765**. Терминал оставьте открытым.
8. Нажмите **Choose File**, выберите `demo/requirement.txt`, затем **Extract product lines**. Или вставьте собственный текст. Одновременно файл и текст не отправляются: очистите ненужное поле.
9. Сверьте позиции с **Original document text**. У последней тестовой позиции отсутствуют количество и единица: подтвердите их вручную по уточнению заказчика. Не считайте вымышленное количество достоверным.
10. Отметьте проверенные строки и нажмите **Save review**. Неизвестные поля можно оставить пустыми и сохранить незавершённую проверку. Полностью подтверждённая запись получит статус **REVIEWED**.
11. **Download saved JSON** скачивает последнюю сохранённую версию для внутренней работы. Этот файл содержит исходный текст, включая информацию о заказчике. Он не предназначен для поставщиков.

## Подготовка запросов поставщикам

Для OCR-заявки перед RFQ обязательно выполните сверку с изображениями из следующего раздела.

1. Раскройте **Supplier directory**. Введите название поставщика, один email и его категории. Нажмите **Save supplier**. Для учебного прогона используйте явно вымышленные контакты на `example.com`; не отправляйте им письма. Рабочий справочник изначально пуст.
2. Чтобы изменить контакт, нажмите его запись в справочнике. Постоянный ID сохранится. Чтобы прекратить использование контакта, снимите **Active supplier** и сохраните. Удаление контакта не используется, чтобы сохранить связи RFQ.
3. Проверьте и сохраните все товарные строки. Для ошибочной или отозванной позиции отметьте **Exclude this position from RFQs** и введите причину. Исключённая строка остаётся в истории, но не попадает в запрос. Нельзя одновременно исключить и одобрить строку.
4. В разделе **Protect customer information** прочитайте предложенный список защищаемых данных. Добавьте все остальные имена/названия заказчика, внутренние ссылки и продажные цены — по одному значению на строку. Сверьте весь исходник. Распознанные заголовки заказчика автоматически сохраняются в защите даже при удалении из поля.
5. Отметьте подтверждение и нажмите **Save privacy checklist**. Если затем меняете список, снова подтвердите и сохраните его до формирования RFQ.
6. Выберите одного или нескольких поставщиков для каждой включённой категории. Нажмите **Prepare RFQ preview**. Если известные конфиденциальные значения обнаружены в товарных полях или сформированном файле, экспорт блокируется. Исправьте поля по исходному документу и сохраните проверку. Не удаляйте реальный секрет из защиты ради прохождения проверки.
7. Просмотрите каждое сообщение и BCC-получателей. Excel содержит только разрешённые товарные поля, новые RFQ-номера и постоянные ID строк; исходные цитаты, имя файла и заголовки заказчика не копируются.
8. Отметьте подтверждение просмотра и нажмите **Approve local export**, затем **Download RFQ ZIP**. Это настоящий локальный архив, а не Gmail-черновик. Письмо автоматически не создаётся и не отправляется.
9. ZIP содержит внутренний `dispatch-manifest.json` со списком поставщиков и, для каждой категории, `email-body.txt` и `reply.xlsx`. **Не отправляйте поставщику ZIP, manifest, внутренний JSON или оригинал заявки.** Если вручную готовите письмо, используйте только проверенный текст и соответствующий `reply.xlsx`; поставщиков помещайте в BCC. Саму отправку этот учебный этап не выполняет.
10. После изменения заявки или поставщика сформируйте новый пакет. Старый архив приложение больше не выдаст, но ранее скачанные копии автоматически отозвать нельзя.

Проверка ищет известные защищаемые значения с нормализацией регистра/пунктуации и денежных сумм; она не способна гарантированно определить неизвестную ей конфиденциальную информацию. Поэтому полнота списка и просмотр человеком обязательны. Ошибка OCR в имени заказчика также требует проверки по изображению. Совпадение с допустимым товарным текстом может блокировать экспорт: проверку нельзя обходить удалением настоящего секрета.

## Скан, фотография или смешанный PDF

1. Выберите PDF, PNG, JPG/JPEG или неанимированный WebP. Для сканов и смешанных PDF включите **Enable local page processing**. Для фотографий это подтверждение обязательно.
2. Прочитайте условие хранения: исходный файл временно сохраняется в локальной базе до окончания/ошибки/отмены обработки. Превью OCR-страниц сохраняются вместе с заявкой до её удаления. Никаких внешних OCR API нет.
3. Нажмите **Extract product lines**. В **Local processing queue** появятся состояние и номер обрабатываемой страницы. Для одной страницы возможны десятки секунд или минуты; лимит одного модельного вызова — четыре минуты. Многостраничный файл обрабатывается последовательно.
4. Можно закрыть вкладку: работа продолжится, если локальное приложение и Ollama работают. Если приложение было прервано, при следующем запуске задача будет заново обработана из сохранённого исходника. Незавершённые результаты не объявляются готовыми.
5. **Cancel processing** отменяет задачу и удаляет сохранённый исходник из очереди. Уже начатый вызов модели может ещё выполняться до ответа/тайм-аута, но его результат не будет сохранён как готовая заявка.
6. После завершения нажмите **Open processed requirement**, если запись не открылась автоматически. Раскройте каждую страницу в блоке OCR и сравните распознанный текст и позиции с изображениями. Превью доступны и после обновления вкладки/перезапуска приложения.
7. Исправьте ошибки в товарных полях; пропущенные позиции добавьте вручную с точной цитатой из распознанного текста. Если OCR полностью пропустил строку, перепишите её с изображения в поле цитаты и укажите номер сохранённой OCR-страницы. Такая позиция будет явно отмечена как ручная расшифровка изображения; исходный ответ OCR останется неизменным в истории. Нельзя ссылаться на отсутствующую страницу.
8. Отметьте **I compared the OCR transcript and product lines with the source page images**, затем **Save review**. Без сохранённой сверки статус REVIEWED и формирование RFQ блокируются, даже если все товарные строки отмечены.
9. Для тестовых файлов выполните `python tests/make_ocr_inputs.py`: они появятся в `data/ocr-inputs/`. Все сведения вымышленные. Там есть PNG/JPEG/WebP, сканированный и смешанный PDF и пустое изображение.

Пустая картинка должна завершаться понятной ошибкой без товарных позиций. Отсутствие предупреждений модели не доказывает правильность OCR. Рукописные, размытые и мелкие надписи отдельно не принимались; проверяйте их по оригиналу. Превью ограничены 2200 пикселями по длинной стороне.

## Последующие запуски

Запустите Ollama, откройте PowerShell в папке проекта и повторите команду из шага 6. Для остановки нажмите Ctrl+C в терминале. Закрытие вкладки браузера не останавливает сервер.

## Где хранятся данные

Текст, исходный ответ модели, сохранённые ревизии, поставщики, RFQ-пакеты, очередь и OCR-превью находятся в `data/workbench.sqlite3`. Обычные TXT/Office/текстовые PDF без фоновой обработки не сохраняются как бинарные файлы. Исходники фоновых задач временно сохраняются до окончания/ошибки/отмены. Кнопка **Delete record** удаляет заявку, её историю, превью и RFQ; поставщики остаются в общем справочнике. SQLite secure_delete включён, но это не обещание удаления копий из резервных копий, SSD или экспортированных файлов.

Папка `data/` исключена из Git. Для резервной копии остановите сервер и скопируйте эту папку в защищённое место. Не публикуйте её в портфолио.

## Ограничения этого этапа

- TXT: UTF-8. PDF: текстовый слой, до 50 страниц. DOCX и XLSX: настоящие Office-файлы, не переименованные DOC/XLS. Формулы в XLSX отклоняются; подготовьте копию со значениями.
- Размер файла до 10 MB. После чтения — до **1 MiB UTF-8 текста**, до 1 000 товарных позиций. Длинные заявки обрабатываются частями до 12 000 байт и восьми распознанных нумерованных блоков за вызов. Один сплошной товарный блок/абзац, превышающий лимит части, отклоняется: приложение не разрывает его посередине характеристик. У OCR одной страницы остаётся отдельный предел ответа 16 000 символов; очень плотные страницы требуют отдельной проверки.
- Изображения: PNG, JPEG и неанимированный WebP до 25 мегапикселей. Сканированные и смешанные PDF обрабатываются локальной vision-моделью после подтверждения хранения. Встроенные изображения внутри DOCX/XLSX пока не поддерживаются: документ отклоняется целиком, чтобы не выдать неполную заявку. Формулы Excel также отклоняются.
- Модель может ошибаться или пропускать позиции. Сверяйте весь документ; пропущенную позицию можно добавить через **Add a missed line**, указав исходный номер и точную цитату.
- Исходные номера, цитаты и постоянные ID уже сохранённых строк защищены от изменения. Исходный ответ модели хранится отдельно от исправленных ревизий. **Saved revision history** показывает сохранённые версии и причины исключений. История начинается с этой версии приложения; ранее перезаписанные или несохранённые правки восстановить нельзя.
- Категории настраиваются в `categories.json` до запуска. Используйте постоянные ID; изменение ID потребует миграции старых записей.
- Компьютер должен быть включён. Это не облачный сервис и не завершение всего заказа.

## Проверки для разработчика

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe tests/make_browser_inputs.py
npm install
npx playwright install chromium
npm run test:browser
```

Для браузерной проверки сервер и Ollama должны уже работать. Тест делает настоящие вызовы модели, создаёт временные записи с вымышленными данными и удаляет их после успешной проверки. При ошибке записи могут остаться для диагностики. Результаты и скриншоты сохраняются в `data/`. Node.js нужен только для этой проверки, а не для работы приложения.

Если порт занят: `python -m rfq_workbench serve --port 8766`, затем откройте `http://127.0.0.1:8766`. Для браузерного теста задайте `$env:RFQ_BASE_URL = 'http://127.0.0.1:8766'`.

Одна база может быть открыта только одним экземпляром приложения. Для параллельного QA используйте отдельный `--database`, как в примерах ниже. Не запускайте второй сервер на той же базе: очередь должна иметь одного владельца.

Для RFQ-теста запустите отдельный QA-сервер с отдельной базой: `python -m rfq_workbench serve --port 8766 --database data/qa-rfq.sqlite3`. Во втором терминале выполните `npm run test:rfq`, затем `python tests/inspect_rfq_package.py data/rfq-browser-package.zip`. Тест использует настоящую локальную модель, скачивает ZIP, проверяет блокировку известного секрета и оставляет вымышленных поставщиков неактивными в QA-базе. Поставщики из теста не добавляются в рабочую базу на порту 8765.

Для OCR: `python tests/make_ocr_inputs.py`, затем отдельный сервер `python -m rfq_workbench serve --port 8766 --database data/qa-ocr.sqlite3` и во втором терминале `npm run test:ocr`. Проверка восстановления: `python tests/queue_restart.py` запускает и прерывает только собственный тестовый процесс на порту 8771; если порт занят, проверка останавливается. Вызовы модели настоящие, платных сервисов нет.

## Длинная заявка

1. Выберите TXT/PDF/DOCX/XLSX или вставьте длинный текст. Включите **Enable background processing** и подтвердите временное локальное хранение. При вставленном тексте приложение помещает в очередь его UTF-8-копию; это не внешний сервис.
2. Нажмите **Extract product lines**. Очередь покажет текущую часть. Дождитесь завершения всех частей: результат одной части не выдаётся за готовую заявку.
3. Откройте результат. Кнопка **View source** у строки выделяет точную цитату в полном исходном тексте. Для PDF показывается исходная страница. Повторяющиеся номера строк допустимы: позиции различаются постоянными ID и местами в исходнике.
4. Сверьте все нумерованные разделы, включая те, по которым не появилась позиция. Такой раздел может быть пропущенным товаром или нетоварным условием — приложение показывает предупреждение, но не придумывает отсутствующий товар.
5. Исправьте и подтвердите товарные поля либо исключите ненужные строки с причиной. Затем отметьте **I compared the complete source...** и сохраните проверку. Без этой сверки статус остаётся NEEDS REVIEW и RFQ недоступен. Для OCR дополнительно обязательна сверка изображений.
6. Простые буквальные пары «количество / единица» в источнике проверяются кодом. Спорные форматы вроде `1,200` или `1.200` автоматически не переосмысливаются. Исходные ответы модели и использованные буквальные значения доступны в JSON/истории анализа.

Для воспроизводимой проверки: `python tests/make_long_inputs.py`, отдельный сервер `python -m rfq_workbench serve --port 8766 --database data/qa-long.sqlite3` и `npm run test:long`. Файлы вымышленные; проверяются 24 позиции, повторяющиеся номера и многострочные характеристики. Само разбиение не доказывает точность модели на произвольных реальных документах.
